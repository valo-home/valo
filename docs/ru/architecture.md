# Архитектура

Как устроен Valo в текущей реализации. Страница для разработчиков, пользователю достаточно остальных разделов. Установка и обслуживание описаны в `src/docs/operations.md` в репозитории.

Документ описывает систему так, как она собрана в `src/valo`. Целевая архитектура и обоснование выбора библиотек лежат в `__prototip__/Умный дом на Zigbee и MQTT. Архитектура, библиотеки и API.md`. Расхождения с целевой архитектурой собраны в последнем разделе

## Назначение

Узел умного дома на Zigbee и MQTT со своим ядром, веб клиентом и расширениями. Zigbee обслуживает Zigbee2MQTT как отдельная программа, ядро общается с периферией только через брокер Mosquitto

## Две среды на одном узле

Одна сборка работает в двух средах одновременно. Среда это отдельный проект Docker Compose со своими томами, поэтому базы, брокеры, Redis и очереди не пересекаются

| | Демо | Рабочая |
| --- | --- | --- |
| Проект compose | valo-demo | valo-real |
| Файл переменных | `envs/demo.env` | `envs/real.env` |
| Профиль compose | demo, служба mocks | zigbee, служба zigbee2mqtt |
| Источник устройств | имитатор Z2M на 36 устройств, устройства hub/v1, HA discovery | стик Zigbee через Zigbee2MQTT, MQTT устройства в локальной сети |
| База | том `valo-demo_pg` | том `valo-real_pg` |
| Вход | http://localhost:3000 | http://localhost:3100 |
| Брокер наружу | 127.0.0.1:1884 | 0.0.0.0:1883 |
| Владелец | `mikko`, создают моки при наполнении | создается мастером первичной настройки |

Ядро не знает, откуда пришли сообщения. Моки публикуют те же топики Zigbee2MQTT, что и настоящий Z2M, поэтому код ядра в обеих средах одинаковый. Разница только в профиле compose и переменной `VALO_ENV`, которая выводится в интерфейс меткой среды со ссылкой на соседнюю среду (`VALO_PEERS`)

## Службы

| Служба | Образ | Роль |
| --- | --- | --- |
| edge | caddy | Единая точка входа HTTP. `/socket.io/*` в ws, `/rtc/*` в cameras после проверки `forward_auth`, `/api/v1/media/*` прямо в backend, остальное в web. Защитные заголовки. HTTPS дает инфраструктура сервера перед edge |
| web | valo-web | SvelteKit на adapter-node. Страницы, вход, прокси `/api/*` к backend с токеном из cookie |
| backend | valo-core | REST API на Litestar, `/api/v1` |
| ws | valo-core | Socket.IO, комнаты по устройствам, помещениям, сценариям, повтор пропущенных событий по номеру |
| mqtt | valo-core | Единственный подписчик брокера. Разбор Z2M, HA discovery, контракта hub/v1, ручных привязок, вызовов расширений. Таймеры сценариев |
| ext | valo-core | Супервизор процессов расширений. Установка, запуск, перезапуск, учетные данные брокера |
| worker | valo-core | Задачи taskiq. Сценарии, таймауты команд, резервные копии, OTA, карта сети |
| scheduler | valo-core | Расписание taskiq. flows.tick раз в минуту, агрегаты истории, очистка, ежедневная копия и ежечасная проверка пропущенной |
| agent | valo-core | ИИ ассистент. Очередь `agent:jobs` в Redis, цикл модель и инструменты, поток ответа в `chat:<id>` |
| cameras | valo-media | Служба видео. Тот же код ядра плюс go2rtc 1.9.15 и ffmpeg 7.1.1. Одно подключение к каждой камере, буфер последних секунд в tmpfs, снимки и клипы по событиям, ротация хранилища |
| init | valo-core | один раз создает секреты служб в томе secrets и папки записей, затем завершается |
| migrator | valo-core (atlas community) | `atlas migrate apply` при каждом старте |
| postgres, redis, rabbitmq | официальные | База, кэш и шина событий для Socket.IO, очередь задач |
| mosquitto | eclipse-mosquitto 2.0 | Брокер MQTT 5 с Dynamic Security |
| zigbee2mqtt | koenkk/zigbee2mqtt 2.13 | Ждет выбора координатора в мастере настройки или на странице Zigbee, доступ к USB устройствам последовательного порта без привилегированного режима. В демо выключен |
| mocks | valo-mocks | Только демо. Имитатор Z2M и наполнение демо данными |

Проверки здоровья есть у backend, ws, mqtt, ext, cameras, web и инфраструктурных служб. Процессы mqtt, ws, ext, cameras и worker пишут пульс в Redis (`beat:<имя>`), проверка `python -m app.lib.alive <имя>` читает его

## Потоки данных

### Состояние от устройства

1. Z2M публикует `zigbee2mqtt/<ieee>` с JSON состоянием
2. Процесс mqtt получает сообщение, `ingest.parse` разбирает JSON и вычищает нулевые символы из строк (их присылают устройства Tuya, PostgreSQL JSONB их не принимает)
3. `ingest.z2m` находит устройство по имени Z2M, `adapters.z2m_in` переводит свойства Z2M в возможности ядра (`state` в `on`, `brightness` 0..254 в `bri` 0..100, `color_temp` в кельвины)
4. `devices.apply` пишет состояние, историю и события, проверяет подтверждение ожидающих команд, после фиксации транзакции рассылает изменение через Socket.IO и запускает сценарии с подходящими триггерами

### Команда

1. Клиент шлет `POST /api/v1/devices/{id}/command`
2. Ядро проверяет права и диапазон, создает команду со статусом pending, `adapters.z2m_out` строит JSON для `zigbee2mqtt/<ieee>/set`
3. Команда подтверждается, когда устройство сообщает новое значение. Без ответа за `COMMAND_TIMEOUT` секунд она получает статус timeout, интерфейс показывает ошибку у элемента управления

Проверено на реальной розетке TS011F 05.11.2026, обе команды (вкл и выкл) подтверждены статусом ok

### Список устройств Zigbee

`zigbee2mqtt/bridge/devices` (retained) превращается в устройства ядра. Возможности строятся из `definition.exposes`. Каждое устройство обрабатывается в своей точке сохранения, поэтому ошибка одного устройства не откатывает весь список. Устройство, впервые увиденное во время интервью, получает имя из описания модели после интервью, если пользователь его не переименовал. Устройства, которых нет в новом списке, удаляются с событием device.removed

### Сопряжение

`POST /api/v1/zigbee/permit-join` публикует `bridge/request/permit_join` и ждет `bridge/response` с тем же transaction. События `bridge/event` (device_joined, device_interview) идут в журнал и в окно сопряжения через Socket.IO

## MQTT

| Пространство | Кто публикует | Назначение |
| --- | --- | --- |
| `zigbee2mqtt/#` | Z2M или моки | устройства Zigbee, запросы и ответы моста |
| `homeassistant/+/+/config`, `homeassistant/+/+/+/config` | сторонние устройства | HA discovery |
| `hub/v1/dev/<id>/{meta,state,set,event,avail,ack}` | устройства и ядро | собственный контракт |
| `hub/v1/ext/<id>/...` | расширения и ядро | вызовы, журнал, статус, устройства расширений |
| `hub/v1/core/resp` | расширения | ответы ядру по correlation data |
| `$CONTROL/dynamic-security/v1` | ядро | учетные записи и роли брокера |

Учетные записи брокера. `valo-core` создается при первом старте mosquitto с правом публикации в `#`. `zigbee2mqtt` и `valo-mocks` создает процесс mqtt при старте, если задан пароль. Устройствам hub/v1 и расширениям ядро выдает отдельные записи с ролями на свои топики. При изменении списка прав роль пересоздается без отключения клиента

## Хранение

- PostgreSQL. Пользователи, токены, дом, помещения, устройства с возможностями и текущим состоянием, команды, события, сырые значения и часовые агрегаты, сцены, сценарии с версиями и трассами, расширения, панели, резервные копии, камеры (`cameras`), события камер (`camera_events`) и записи (`media`). Схема в `backend/src/app/db/models`, миграции Atlas в `backend/migrations`
- Redis. Кэш сведений Z2M, индекс топиков ручных привязок и HA, таймеры сценариев (`timers`), ожидающие команды, журнал обозревателя MQTT, поток событий реального времени для повтора после обрыва, пульс процессов
- Тома. `data` (резервные копии и установленные расширения), `z2m` (база и конфигурация Z2M, копия координатора), `mosquitto` (dynsec.json и персистентность)
- Записи камер. Папка хоста `MEDIA_ROOT` монтируется как `/media-root` в backend, worker, mqtt и cameras, в контейнер ext никогда. Буфер видео в tmpfs `/buffer` службы cameras (`CAMERAS_BUFFER_SIZE`, по умолчанию 512m)

## Резервные копии

`POST /api/v1/system/backups` или ежедневная задача в 01:30 UTC. Если копии по расписанию нет больше 26 часов (узел был выключен), задача backups.catchup в 50 минут каждого часа делает ее сразу. Архив `tar.gz` содержит `pg_dump` базы, архив данных Z2M (запрос `bridge/request/backup`) и `meta.json` со списком расширений и их настроек. Хранится в томе `data` и дублируется в папку на другом диске (`BACKUP_MIRROR_HOST`), число копий ограничено `BACKUP_KEEP` в обеих папках. В `meta.json` записан идентификатор копии, по нему после восстановления запись этой копии в базе получает статус ok (снимок базы делается, пока запись еще в статусе running). Копии, зависшие в running дольше часа, не блокируют создание новых

Восстановление (`POST .../restore`, только владелец) выполняет `pg_restore --clean --single-transaction`, затем чистит кэши привязок в Redis, переподписывается на брокер, чтобы получить retained сообщения заново, и перестраивает индекс сценариев. Данные Z2M из архива автоматически не восстанавливаются, их переносят в том `z2m` вручную при замене узла

## Журнал ошибок

`app.lib.errlog.Handler` подключается в `log.setup` каждого процесса ядра и пишет записи уровня error в Redis с группировкой по процессу, источнику и событию. Ошибки сервера web передает хук `handleError`, ошибки браузера отправляет клиент (`window.onerror`, `unhandledrejection`, не больше 10 за загрузку страницы, 30 в минуту на пользователя). API `GET/DELETE /api/v1/system/errors`, `POST /api/v1/system/errors/seen`, `POST /api/v1/system/errors/report`. Внешних систем мониторинга нет, данные не покидают узел

## Типы устройств

Возможности Zigbee строятся из `exposes` Z2M. Поддерживаются логические, числовые, перечисления, текст и цвет (`color_xy`, `color_hs`, значение `#rrggbb`, команда уходит как `{"color": {"hex": ...}}`). Каналы многоканальных устройств получают суффикс (`on_l1`, `on_l2`), замок дает возможность `locked`, вентилятор `fan_mode`. Виды устройств для иконок и сводок: свет, реле, розетка, климат, термоголовка, кнопки, движение, контакт, протечка, дым, шторы, счетчик, замок, вентилятор, погода, качество воздуха, календарь, таймер, будильник и прочие. Графики `bars` рисуют отрицательные значения ниже нулевой линии (температура, отрицательные спотовые цены). Интерфейс рисует элемент управления по типу возможности, поэтому новое устройство управляется без доработки клиента

Сущности. Расширение это программный модуль из каталога. Устройство это прибор, подключенный по Zigbee, MQTT (включая HA discovery и сопоставление топиков) или через расширение. Сервис это запись расширения без своего прибора. Расширение само объявляет запись сервисом или устройством (`ext.device(..., service=True/False)`, хранится в `attrs.meta.service`), без объявления действует запасной список видов: погода, качество воздуха, календарь, будильник, таймер, счетчик, присутствие, контроль розеток (`devices.is_service`, поле `service` в API). Страница Устройства показывает два списка, Устройства и Сервисы, фильтр источника строится из имеющихся источников (Zigbee, MQTT, имена расширений). Ответ `GET /extensions/contributions` содержит `exts` (id, имя, значок, состояние, число блоков и шаблонов), карточка расширения по нему и по устройствам показывает, что расширение добавило. Они не входят в число устройств в меню, на странице Устройства, в счетчике неразмещенных на обзоре и в ответах ассистента. Устройства, которые расширение подключает (например симулятор), считаются устройствами

## Расширения, данные и интерфейс

- Секретные настройки (тип `secret`, например токен бота) хранятся в базе зашифрованными (Fernet, ключ из `VALO_SECRET_KEY`, если не задан, выводится из `JWT_SECRET`). API их не отдает, только список заданных секретов. Процесс расширения получает расшифрованные значения в окружении при запуске
- Описание расширения лежит в пакете `docs/<язык>.md` и доступно через `GET /api/v1/extensions/{id}/docs` до установки
- Расширение может принести шаблоны сценариев (`templates` в манифесте), они появляются в общем списке шаблонов
- Декларативные страницы расширений поддерживают блоки `hero`, `strip`, `clock`, `stats`, `bars`, `list`, `text` и `actions` (кнопки, которые вызывают метод страницы с `action`)
- Блок `hero` это сводка с главным значением: `icon`, `tone` (цвет темы `amber`, `frost`, `violet`, `ok`, `warn`, `crit`), `value`, `unit`, `digits`, `text`, `sub` (строка или части `{label, value | range, unit, digits}`, через точку) и `items` (показатели `{icon, label, value, unit, digits}`, в виджете только значок и значение, на странице с подписью). В широком виджете показатели встают справа. Блок `strip` это лента по времени: `items: [{label, icon, tone, value, unit, digits, sub}]` и `now` (выделенная ячейка), показывает столько ячеек, сколько помещается в ширину
- Формат блоков. Числа передаются числами с `unit` и `digits`, форматирует клиент по языку, единицы переводятся (`u.<единица>`). Строка блока `list` может содержать `value` числом или `values` (части `{value, unit, digits}`, `{range: [от, до], unit}`, `{text}`), действие в строке `action: {key, label, icon, hint}` или массив `actions`. Блок `bars` принимает `unit`, `digits`, `series: [{label, color}]` и `kinds` (номер серии для каждого столбца), показывает минимум и максимум, легенду и значение при наведении и фокусе
- Блок `clock` рисует живые время, дату с днем недели и годом и номер недели в часовом поясе дома, его используют страница и виджет календаря
- Виджет расширения может объявить параметры (`params` в манифесте). Тип `place` дает в настройке виджета поиск места через страницу расширения `geocode`. Геокодер Open-Meteo ищет только по названиям на языке запроса, поэтому расширение спрашивает его параллельно на языке интерфейса, украинском, русском и английском, объединяет места по `id` и для найденных на другом языке берет название на языке интерфейса (`/v1/get`), выбранное место (`place: {name, lat, lon}`) хранится в виджете и передается в запрос страницы виджета. Open-Meteo по нему берет прогноз для города и кеширует его на 30 минут, без места используются координаты дома
- Сетка панели строится шагами высоты 164 px с зазором 16 px, виджет занимает 1, 2, 3 или 4 шага (поле `h`) и 1 или 2 колонки (`size: "wide"`). Без `h` высота подбирается автоматически: наименьший шаг, в который помещается естественная высота содержимого (замер через ResizeObserver, растяжение графиков в замер не входит). Свободное место по высоте отдается графику (`.grow` с `data-base`), лишнее содержимое прокручивается внутри карточки. В режиме настройки кнопки ширины и высоты показывают текущее значение и переключают его по кругу
- Настройка открывается у любого виджета панели. Общий параметр `title` (до 60 символов) заменяет заголовок по умолчанию, пустое поле возвращает его. Длинное текстовое значение в блоке `stats` занимает всю строку плиток
- Имя устройства расширения задается строкой или словарем по языкам, SDK выбирает язык дома. Новое имя от расширения применяется к существующему устройству, пока пользователь не переименовал его сам (`attrs.nameSet`)
- Документация продукта лежит в `src/valo/docs`: `index.json` задает разделы и порядок страниц, страница это `<язык>/<страница>.md` (ru, uk, en, остальные языки берут en, затем ru). Ядро отдает ее через `GET /api/v1/help` (разделы, страницы с заголовками из первой строки, расширения каталога с описанием) и `GET /api/v1/help/{страница}`, поиск через `GET /api/v1/help?q=` ранжирует абзацы и заголовки. В образ ядра папка попадает как `/app/help`, оттуда же ее читает ассистент (`search_docs`, `read_doc`). Веб клиент показывает раздел `/docs` с оглавлением, поиском и описаниями расширений из пакетов (`/docs/ext/<id>`)
- Подсказки `Hint` (значок вопроса) стоят у заголовков страниц и у неочевидных вкладок и колонок. Текст из ключа `hint.<имя>`, ссылка ведет на страницу документации. Подсказка открывается наведением, фокусом или нажатием, закрывается Escape и щелчком мимо, позиционируется `fixed`, поэтому не обрезается таблицами и вкладками
- Markdown в документации, описаниях расширений и чате понимает заголовки, абзацы, списки, жирный, код, таблицы и ссылки. Внутренние ссылки `/docs/...` получают префикс языка, внешние открываются в новой вкладке, другие схемы выводятся текстом
- Запрос страницы расширения с `action` требует роль жильца и выше, без `action` хватает гостя. Ядро добавляет в параметры поле `role` с ролью пользователя, значение из запроса перезаписывается. Гостю кнопки действий в виджетах и на страницах расширений недоступны
- Настройка расширения типа `devices` дает выбор нескольких устройств галочками и хранит id через запятую, список сужают `caps` и `access`. Подпись и пояснение настройки берутся из `prm.<key>` и `prmh.<key>`, а если их нет, из `name` и `hint` манифеста
- Расширение `fi.valo.safety` (Безопасность дома) следит за датчиками протечки, дыма, угарного газа и газа, ведет инциденты, при протечке под охраной выключает выбранные устройства, напоминает о батарее, связи и проверке датчиков дыма. Его запись вида `safety` объявлена сервисом (`service=True`), переключатель охраны у нее остается. Расширение `fi.valo.plugguard` (Контроль розеток) отключает розетку при перегрузке и в долгом ожидании и ведет учет за день, его запись вида `plugguard` это сервис
- Тексты интерфейса поддерживают формы множественного числа: `{n, plural, one {# виджет} few {# виджета} many {# виджетов} other {# виджета}}`, форму выбирает `Intl.PluralRules` по языку
- Обновление, которое требует новых прав, выполняется только после подтверждения этих прав, недостающие настройки дополняются значениями по умолчанию из нового манифеста
- Код версии копируется в `/data/extensions/<id>/<версия>` при установке и обновлении, данные расширения лежат рядом в `data` и переживают обновления. Измененный код публикуется только с новым номером версии
- Блок расширения вида cond может вернуть выход `[порт, словарь]`, ключи словаря становятся переменными текста следующих блоков. Встроенные переменные со значением (`{time}`, `{date}` и другие) имеют приоритет, пустые (`{room}`, `{device}` без устройства в событии) заполняются из данных события. Поэтому даты и время расширений называются иначе (`{day}`, `{at}`)
- При удалении расширения ядро удаляет его устройства и очищает retained сообщения `hub/v1/ext/<id>/dev/<dev>/{meta,state,avail}` на брокере. Описание устройства от неустановленного расширения игнорируется, поэтому удаленные устройства не возвращаются после перезапуска службы mqtt
- SDK. `ext.changed(*keys)` сообщает ядру, что данные страниц или виджетов с этими ключами изменились (топик `hub/v1/ext/<id>/changed`)
- SDK. `ext.available(dev, online)` помечает устройство расширения как доступное или нет. Ошибка `ValueError` в обработчике команды считается неверным вводом и пишется предупреждением, остальные ошибки попадают в журнал ошибок

## Камеры и медиа

Камеры входят в слой медиа ядра, подключение к камерам конкретных марок делают драйверы в виде расширений. Камера это запись `cameras` (драйвер, конфигурация, потоки, сведения о модели, правила записи) с устройством вида `camera` и возможностью `occ`. События камер хранятся в `camera_events` (метка, источник, оценка, начало и конец, ссылки на снимок и клип), снимки и клипы в `media` (камера, событие, вид, путь, размер, длительность, происхождение)

- Добавление. `POST /api/v1/cameras/probe` и `POST /api/v1/cameras` вызывают у драйвера `camera.probe` с полями из `manifest.camera.fields`. Драйвер возвращает адреса потоков и снимков, ядро шифрует их (secretbox) вместе с секретными полями. После каждого изменения ядро шлет драйверу `camera.sync` со списком его камер (задача `cameras.sync_driver`) и публикует `cameras:changed` в Redis
- Служба cameras (`app.cameras.main`) по `cameras:changed` перечитывает камеры (`cameras.sources`, единственное место, где адреса расшифровываются) и пишет конфигурацию go2rtc. API go2rtc слушает `:1984` с базовым путем `/rtc`, RTSP `:8554`, оба с паролем, выведенным из секрета ядра. WebRTC выключен, браузер получает видео через WebSocket и MSE
- Доступ к видео. Caddy направляет `/rtc/*` в cameras только после `forward_auth` на `GET /api/v1/cameras/rtc-auth`. Ядро пропускает только пути `/rtc/api/ws`, `/rtc/api/frame.jpeg` и `/rtc/api/stream.mp4`, проверяет сессию, роль жильца и доступ к помещению камеры по имени потока и возвращает заголовок авторизации go2rtc. Браузер знает только имена потоков (`<id камеры>` и `<id камеры>_sub`)
- События. Драйвер или расширение распознавания вызывает `cameras.event`. Ядро открывает или закрывает событие, меняет возможность устройства, запускает сценарии с триггером `camera_event` и публикует событие в `cameras:events`
- Запись. Для камер в режиме `events` служба держит непрерывную запись основного потока кусками по 2 секунды без перекодирования и без звука (`-an`) в `/buffer`, хранится около 40 секунд. По началу события сохраняется снимок, по концу клип склеивается из кусков от `pre` до `post` секунд вокруг события с ограничением `max`. Ручные клипы и клипы сценариев идут через `cameras:jobs`, в режиме `off` записываются прямо из потока
- Хранилище. Корень `/media-root`, папка внутри него и пороги в настройках дома (`settings.media`). Раз в минуту и перед каждым клипом `media.rotate` удаляет записи по сроку, по лимиту объема и пока свободного места меньше порога, только по своим записям в `media`. Если место не освободилось, клипы не пишутся, держится уведомление `media_low_space`
- Расширения получают камеры и записи только вызовами ядра по правам `cameras.provide`, `cameras.stream`, `cameras.events`, `media.write`, `media.read`. Для анализа `cameras.stream` выдает внутренний адрес RTSP go2rtc, поэтому камера держит одно подключение
- Блоки сценариев. Триггер `camera_event` (камера, метка, начало или конец), действия `snapshot` и `clip`, переменные `{label}` и `{snapshot}`. Виджет панели `camera` показывает снимок `/api/v1/cameras/<id>/preview` раз в 10 секунд

## ИИ ассистент

Чат с ассистентом доступен каждому пользователю, ассистент действует с его правами. Модель подключается через OpenAI SDK к OpenRouter или совместимому API (`app/lib/llm.py`), адрес, модель, ключ, температура, число шагов и дневной лимит задаются в Система, ИИ. Ключ хранится в таблице `ai_settings` зашифрованным (secretbox) и не отдается API

Поток. `POST /api/v1/chats/<id>/messages` сохраняет сообщение, переводит чат в `running` и кладет задание в список Redis `agent:jobs` с правами пользователя (роль, ограничения токена). Служба `agent` (`app/agent/main.py`, до 3 заданий параллельно) собирает системную подсказку и последние 40 сообщений, вызывает модель потоком и выполняет вызовы инструментов, до `max_steps` шагов. Куски текста идут событием `chat_delta`, шаги `chat_step` (без записи в поток повтора), сообщения `chat_msg`, действия `chat_action` в комнату `chat:<id>`, сводка чата `chat` в комнату `user:<id>`. Остановка через ключ `agent:stop:<id>`, признак работы `agent:busy:<id>` с TTL 60 с, зависшие чаты сбрасываются при старте службы

Инструменты (`app/domain/assistant_tools.py`) вызывают функции ядра, поэтому права, проверки и события те же, что у интерфейса. Оболочки, записи файлов и прямой записи в базу нет

| Вид | Инструменты | Поведение |
| --- | --- | --- |
| чтение | обзор дома, устройства, устройство, история, помещения, панели, каталог виджетов, сценарии, блоки, сцены, расширения, Zigbee, журнал, поиск и чтение документации, чтение исходного кода ядра (администратор) | результат до 12 000 символов |
| запись | помещения, привязка устройств, переименование, создание и изменение панелей и виджетов | выполняются сразу, действие с данными для отмены, кнопка Отменить в чате |
| подтверждение | команда устройству, сцена, удаление панели или помещения, создание, изменение, удаление и запуск сценария, установка расширения, сопряжение Zigbee | создается действие `pending`, выполняется кнопкой Выполнить от имени пользователя |

Виджеты от ассистента проверяются: тип, существующее устройство в доступном помещении, числовая возможность для показателя и графика, существующее помещение, установленный виджет расширения. Документация в образе лежит в `/app/docs` (архитектура и эксплуатация) и в описаниях расширений, исходный код ядра в `/app/src`

Таблицы `chats`, `chat_messages` (роли user, assistant, tool, note), `chat_actions` (pending, done, failed, rejected, undone). Демо среда использует демонстрационную модель из моков (`valo_mocks/llm.py`, OpenAI совместимый поток на `mocks:8090`), она отвечает по правилам и проверяет весь путь без ключа OpenRouter

## Обновления в реальном времени

Ядро после фиксации транзакции вызывает `realtime.emit(событие, данные, комнаты)`. Событие пишется в поток Redis `rt:stream` (номер `seq`) и рассылается через менеджер Socket.IO в Redis, служба `ws` доставляет его клиентам по комнатам. При переподключении клиент передает последний `seq` и получает пропущенное, при слишком старом номере перечитывает `/overview`

| Комната | Кто в ней | Что приходит |
| --- | --- | --- |
| `all`, `rooms:all` | пользователи без ограничения по помещениям | устройства, команды, сценарии, сцены, помещения, панели, уведомления, журнал |
| `room:<id>` | пользователи с доступом к помещению | то же по устройствам помещения |
| `any` | все вошедшие | `ext_page` с полями `ext` и `keys`, без данных. Виджет или страница расширения перечитывает данные своим запросом с проверкой прав |
| `dev:<id>`, `flow:<id>` | по подписке страницы устройства или сценария | события и запуски |
| `zigbee`, `mqtt`, `extlog:<id>` | администратор по подписке | сопряжение, поток MQTT, строки журнала расширения (`ext_log`) |

Короткоживущие события (`ext_page`, `ext_log`) не пишутся в поток повтора (`durable=False`), после переподключения страница перечитывает данные. Опрос по таймеру остался только как страховка: виджеты расширений раз в 10 минут, графики виджетов раз в 15 минут (новые точки добавляются из событий `state`), состояние узла раз в минуту

## Списки и постраничный вывод

Растущие журналы читаются порциями по курсору: события (`/events`, `/devices/<id>/events`, параметр `before` с id), команды устройства и запуски сценария (`before` со временем `createdAt` или `startedAt`), `limit` до 200. Ответ остается массивом, признак продолжения это полная порция. Клиент использует `pager` и кнопку «Показать еще», новые записи из сокета добавляются сверху. Списки, которые клиент держит целиком (устройства, Zigbee, сценарии, пользователи, токены, копии, ошибки), выводятся страницами по 25 или 50 (`Pages`). Ветки дерева топиков MQTT показывают первые 100 узлов с догрузкой

## Панели

План дома на обзоре показывает устройства значками с иконкой и цветом состояния. Положение значка хранится в геометрии помещения (`geom.devs`, доли от размера помещения, сервер проверяет формат), нерасставленные устройства выстраиваются рядом внизу помещения. Редактор плана открывается на обзоре и на странице Помещения, двигает помещения и значки мышью, касанием и стрелками. Виджет на панели настраивается на месте, удаление виджета подтверждается вторым нажатием. Страницы расширений в меню сворачиваются в пункт Страницы, если их больше трех. Выбранная вкладка страниц Сценарии, Zigbee, MQTT и Система хранится в адресе (`?tab=`)

Страница `/boards` показывает список панелей с числом виджетов и их составом, `/boards/<id>` открывает панель. Старые ссылки `/boards?board=<id>` перенаправляются. Создание, настройка и удаление доступны участнику и выше, гость только смотрит

Виджеты: устройство (все показания, управление, заряд, время обновления), датчик (температура и влажность, минимум и максимум за сутки, график), розетка (мощность, напряжение, ток, расход за сегодня по счетчику и всего, график мощности), термостат, показатель, график за сутки, неделю или месяц, помещение, свет помещения, сцены, требует внимания, батареи, нагрузка, протечки, двери и окна, часы и погода, виджеты расширений (раздел Сервисы). Ширина обычная или двойная (`size: "wide"`). Расход за сегодня считается по истории счетчика `kwh` с начала суток в часовом поясе дома, уменьшение больше чем вдвое считается сбросом счетчика

## Задачи и очередь

taskiq поверх RabbitMQ доставляет задачи по схеме хотя бы один раз. Задачи с необратимыми действиями (резервная копия, восстановление) получают одноразовый токен в Redis и общую блокировку, повторная доставка не приводит к повторному выполнению

## Вход и сессия

Вход, первичная настройка и выход сделаны обычными формами SvelteKit (действия `+page.server.js` в `login`, `setup`, `logout`), работают и без JavaScript, с JavaScript отправляются через `use:enhance` без перезагрузки. Токен сессии хранится в cookie `valo_token` (HttpOnly, SameSite=Lax, Secure при https). Защита SvelteKit от межсайтовых форм сравнивает Origin с адресом сервера, который adapter-node 6 строит из `PROTOCOL_HEADER` и `HOST_HEADER` (их задает compose за Caddy). Без этих заголовков adapter-node считает адрес https и отклоняет формы по http. Прокси `/api` веб клиента подставляет токен из cookie только если клиент не передал свой заголовок `Authorization`

## Безопасность

- Вход по паролю (argon2), сессия JWT в cookie HttpOnly, токены API с правами read или full и ограничением по помещениям, роли owner, admin, member, guest
- Лимит 10 попыток входа в минуту на адрес клиента. Адрес берется из `X-Forwarded-For` только от доверенных прокси (`TRUSTED_PROXIES`, по умолчанию сети Docker). Цепочка edge, web, backend передает реальный адрес клиента, подмена заголовка клиентом не проходит, потому что web берет последний адрес, добавленный Caddy
- CSP с nonce для скриптов SvelteKit, `frame-ancestors 'self'`, внешние скрипты запрещены. Caddy добавляет `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, `Permissions-Policy`
- Изолированные виджеты расширений работают в iframe с `sandbox="allow-scripts"` без доступа к cookie
- Пароли камер, ключи API и адреса потоков хранятся зашифрованными, в браузер уходят только имена потоков. Видео проходит через edge с проверкой сессии, папка записей не монтируется в контейнер ext
- Брокер без анонимного доступа. В рабочей среде порт 1883 открыт в локальную сеть для MQTT устройств, в демо только на 127.0.0.1
- HTTPS обеспечивает инфраструктура сервера. Caddy доверяет `X-Forwarded-*` только от `EDGE_TRUSTED_PROXIES`, поэтому браузер из локальной сети не может подменить свой адрес

| Один процесс ядра, SQLite по умолчанию, без Redis и RabbitMQ | Несколько процессов на одном образе, PostgreSQL, Redis, RabbitMQ, taskiq | Ядро собрано на шаблоне DevPower. Работает, но тяжелее для одноплатного компьютера |
| Метрики Prometheus, Sentry, OpenTelemetry по выбору | Только внутренний журнал ошибок в Redis с просмотром в вебе | Данные не покидают узел, внешняя инфраструктура не нужна |
| Mosquitto 2.1 и плагин sqlite persistence | Mosquitto 2.0.22 со встроенной персистентностью | 2.1 на момент сборки не выпущена в официальном образе |
| SvelteKit SPA на adapter-static, раздача ядром | SvelteKit на adapter-node за Caddy | Серверная часть web проксирует API и хранит токен в cookie HttpOnly |
| Z2M дочерний процесс ядра | Z2M отдельная служба compose, конфигурация из переменных | Проще обновлять и перезапускать |
| Bits UI, Lucide | нативные элементы и иконки прототипа | Решение за K |
| Камеры и видео вне рамок | Камеры часть слоя медиа ядра (служба cameras на go2rtc), драйверы камер расширения | Видео с камер нужно в одном интерфейсе с устройствами и сценариями, подключение к камерам вынесено в драйверы, как подключение устройств |
